id: SR-256
title: Record files merge field by field, and a same-field clash becomes...
feature: FEAT-007
statement: iaso's merge driver merges a record file field by field against the merge base, so links, independent
  fields and examples added on either side merge on their own; an example number added on both sides is
  renumbered and its links follow, and the driver is declared once however often it is installed. When
  both sides change the same field differently, the record stays readable, carries one intent conflict
  holding the base, both versions and their branch labels, and is unconfirmed; every iaso surface that
  lists it (the merge check, drift, status, the brief) shows it once, as that conflict, until it is settled,
  and a later merge that meets the same record again keeps the open conflict. The owner arbitrates it
  as P3 says; the chosen version is taken, logged with the owner's words, and the record is confirmed
  again when that version was; with no judge the question carries no recommendation; then nothing about
  it remains.
examples:
- id: EX-1
  given: one side adds a verified_by link to SR-005 and the other side adds an implemented_by link
  when: git merges them
  then: SR-005 has both links and nothing conflicts
- id: EX-2
  given: one side changes SR-005's title and the other adds an example EX-4
  when: git merges them
  then: the result has the new title and EX-4, with no intent conflict
- id: EX-3
  given: both sides add a new example numbered EX-3 with different content
  when: git merges them
  then: the incoming one becomes EX-4 and its verified_by link's example is rewritten to EX-4
- id: EX-4
  given: iaso installed its merge driver twice in one repository
  when: .iaso/.gitattributes and git config are read
  then: the record driver is declared once and other attributes are kept
- id: EX-5
  given: main changed SR-005's statement one way and feat-x changed it another way
  when: feat-x is merged into main
  then: SR-005 carries one intent conflict with both statements and the labels main and feat-x, and SR-005
    is unconfirmed
- id: EX-6
  given: a merge left the "deadline reminders" requirement with two versions
  when: the merge check runs
  then: the merge waits, names the conflict once by the requirement's title, and lists nothing else about
    it
- id: EX-7
  given: the same two versions
  when: the drift report and the status are shown
  then: the requirement appears once, as an intent conflict waiting for the owner's answer
- id: EX-8
  given: the owner answers, through the question tool, keep feat-x's version of "deadline reminders"
  when: the drift report runs
  then: nothing about "deadline reminders" remains
- id: EX-9
  given: the owner's answer keeps feat-x's version of "relay checks"
  when: the answer is recorded
  then: the record takes feat-x's statement, the conflict is gone, the resolution is logged with the owner's
    words, and the record is confirmed again if feat-x's version was confirmed
- id: EX-10
  given: no judge is reachable
  when: the conflict is put to the owner
  then: the question says no recommendation is available and why, and answering works the same
- id: EX-11
  given: SR-005 still carries an open intent conflict between main and feat-x
  when: feat-y, which changed SR-005 again where main also changed it, is merged
  then: git leaves SR-005 unmerged with both versions in the file; the open conflict and feat-x's statement
    are kept and no new conflict replaces them

    status shows nothing left about it.'
