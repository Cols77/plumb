id: INT-085
title: Parallel work by awareness; the merge is the one hold
quote: We should always work from a clean or managed environment. If there could be a hook that automatically
  understands what test is connected to what requirement and run them automatically based on stale detection,
  that would be great. And also of course stale detection should also be a hook and be resolved as soon
  as possible. I'd rather not run iaso test full if possible and only perform targeted validation as
  much as possible unless you see an issue with this.
readback: 'Several agents, worktrees and clones work on one repository at once, kept in step by awareness
  rather than locks: each line of work shares the intent it has in flight, record files merge field by
  field, and record ids never collide. A same-field clash or a contradicting capture becomes one intent
  conflict that you arbitrate through a question. The merge is the one place where unapproved or conflicting
  intent is held; nothing else stops the work.'
will:
- Share each branch's intent in flight with every other worktree, read-only and cheaply, and tell the
  agent when another branch changes the same record.
- Merge record files field by field, so only a real same-field clash becomes an intent conflict.
- Put a contradiction between two lines of work to you as one question (question tool; none goes to the
  study room, INT-114), before anything is built when it is caught at capture.
- Reserve record ids through a shared git ref and renumber the ones that still collide across clones at
  the merge, without rewriting history.
- Hold a merge, a rebase step or a push, and only those, while a conflict is open, ids collide, links
  are stale, a question waits, a test fails or the log is broken (DEC-252, DEC-255); touched intent
  still unapproved and paths no commit declares are listed in the full report and never hold. The merge
  check prints only what holds (SR-374, INT-114).
wont:
- Locks, leases, admission or any shared mutable runtime state; a claim is a signal, never a lock.
- Transaction machinery, candidate checkouts or a test run at merge time; at push only the covering tests
  run, and the full suite only when full verification is pending (P10).
- Rewriting git history.
- Let the agent pick the side of an intent conflict that no recorded intent or answer of yours settles.
- Ask you to type a command or name a record id to settle a conflict or approve a merge.
assumptions:
- A touched requirement counts as approved at the merge when you approved it or the judge cascade validated
  it against your words (P3, P9); judge approvals are listed in the merge report and you reverse one by
  saying so.
- A new link or a trace exemption added on a branch is approved the same way as a record, never on the
  agent's word alone.
- The quick merge-time check and the pre-push hook are installed when iaso adopts a repository; a hook
  iaso did not write is left alone.
- 'Superseded in part by INT-114 (DEC-400, the owner''s answer of 2026-10-27, "Newer decisions replace
  them"): the narrower holds of DEC-252 and DEC-255 replace the longer list above, and the merge check
  prints only what holds.'
- Settling an intent conflict from an answer you already gave on the same two versions is resolving from
  recorded intent (P5), not the agent choosing.
