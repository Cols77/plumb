> Status: proposed; semantic adoption remains subject to the existing per-SR human consent workflow.

Drafted 2026-09-28 by the JEV-REVIEW-INTEGRATION planning run; revised the same day on
the human's direction (latest model alias, confidence-tiered routing following
TypeSafe's documented 0.9/0.5 tiers), and again after the human reviewed the draft:
rather than being silently active or inactive, the adapter detects a missing key in an
interactive session and asks the user to paste one; the agent stores it; a user with no
key is bypassed; a user with a key is in. The adapter is the single doorway to
TypeSafe's Jev System One model: `substrate/judgment/` owns the client protocol, the
TypeSafe implementation, the deterministic fake used by CI, the key-onboarding state,
and the `jev:` config in `.factory/factory.yaml`.

Two vendor cautions are encoded rather than ignored. TypeSafe recommends pinning a
version when thresholds are tuned; the human chose the latest alias, so the adapter
records the resolved version and suspends automatic acceptance on drift instead of
pinning. TypeSafe's own evaluation describes confidence as "an escalation signal, not a
certificate" (not verified, T-075 V16) and shows thresholds that do not transfer across workloads; hence
per-action thresholds and the re-validation rule in AC-4.

**AC-3 revised 2026-09-29 by planning run FEAT-023 (answer a36).** The owner chose to
amend this authority invariant rather than route around it. Judgment values may satisfy
the [[SR-085]] points, but only through that policy and only for an active calibrated
claim kind. Challenge dispositions, `sim_human_visualization`, and merge or push
authorization stay human-only. The revision changes this SR's hash, so it needs fresh
consent.

Pasting a key is the user's data-egress decision: repository-derived material is sent
to api.typesafe.ai. The key lives in the user-level secret store, travels via
`TYPESAFE_API_KEY`, and is never repository state. Related: [[SR-078]], [[SR-079]],
[[SR-080]], [[SR-081]], [[SR-082]], [[SR-083]], [[SR-084]]; requiredness model
[[SR-010]]; constraints [[SR-044]], [[SR-037]], [[SR-050]], [[SR-072]].
