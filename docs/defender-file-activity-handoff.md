## Proposed changes in order

1. **Remove the duplicate head read inside each locked append.** In `src/plumb/log.py`, `append()` around line 631 calls `_head()` (line 602), which reads `log-head.json`, then `_set_head()` (line 620), which reads the same file again under the same `_Lock`. Each verdict therefore causes two head reads and one atomic replacement. Reuse the head document loaded within that critical section, preserving both streams and the existing missing/corrupt-head recovery behavior. Do not cache the head across unlocked operations or across processes without validation. A healthy-head append should require one head read; the reproduction's 302 reads should fall to approximately 151, while all verdict entries remain intact. This is a narrow improvement, not a claim that it will remove most CPU use.

2. **Reduce repeated append bookkeeping for a job's verdicts.** `src/plumb/understand/worker.py::_write_applied()` around line 205 calls `log.append()` separately for every verdict. The 160-record test therefore creates/removes the log lock and replaces the head 160 times despite having only four jobs. Evaluate a bounded batch append that preserves one immutable entry per verdict, hash-chain ordering, exclusive writing, and recovery after a partial failure. Updating the head less frequently needs explicit crash/recovery handling: merely leaving an old head pointing at an existing file is not sufficient because `_head()` currently trusts that pointer. Measure this separately from the duplicate-read change.

3. **Avoid redundant progress writes while preserving liveness.** `_Pass.execute()` in `src/plumb/understand/worker.py` writes progress around lines 340 and 361, before and after recomputing inputs. `backlog.after_job()` writes the new count or final line. This produced three progress writes for each of the 31 executed jobs in the 150-record test. `Reporter.update()` in `src/plumb/progress.py` around line 150 always calls `_write()`; terminal redraw throttling does not limit these disk writes. Deduplicate unchanged semantic state within a reporter, with a bounded heartbeat interval. Publish changed steps/counts and completion/failure immediately. Preserve stale-progress detection and worker heartbeat behavior; do not suppress all progress in tests. Verify whether the two initial updates are equivalent for the affected jobs before coalescing them.

4. **Reduce redundant worker passes in the test helper and retain fresh state.** `tests/understand/test_backlog.py::run_pass()` around line 67 enumerates every job file and calls `worker.run_once(open_core(repo), session, job_id)` for each. The 150-record test makes 30 calls for the initial run, another 30 for the already-completed pass, then 31 after changing one record: 91 lock cycles for 31 executed jobs. Each `_Pass.run()` also reloads the whole queue before checking the selected job's result, creating quadratic queue-reading work in this helper. Exercise the actual multi-job worker path for a complete pass where appropriate, retaining explicit tests of completed-job skipping, partial passes, dependencies, and changed-record rejudging.

   Correctness constraint: `Core.events()` in `src/plumb/api.py` caches events per instance. `Core.log_append()` invalidates that cache, but `_write_applied()` calls `log.append()` directly. A single reused Core may therefore retain events from before an earlier job's writes. Address or explicitly refresh that state before consolidating passes. The current helper's repeated `open_core()` avoids this stale-cache issue at the cost of reloading/rebuilding `log-events.json`. Do not hide it by weakening assertions or simply reusing a Core.

The isolated counts showed ordinary lock acquisition/release rather than a lock-retry storm. Focus first on excess operations; do not remove synchronization or lengthen retry sleeps on the assumption that contention caused the measured activity.

## Validation for the fixes

Keep the owner's existing tests running. Use separate temporary repositories for the investigation and regression tests, and retain antivirus settings unchanged so comparisons remain meaningful.

- Add focused assertions for reduced file operations at the responsible interfaces. Also verify both log streams, hash-chain integrity, concurrent writers, missing/corrupt/stale heads, and recovery after interrupted writes where affected.
- Verify that one real worker pass processes multiple jobs with fresh events, correct cumulative progress and final cards. Preserve the existing no-rerun, changed-record, interrupted-pass, and partial-pass behavior.
- Verify that identical rapid progress updates are coalesced, while changed state, final/failure state, and timed heartbeats remain observable. Use controlled clocks rather than sleeps for these assertions.
- Repeat the two instrumented tests and compare operations per executed job/verdict. Keep the 150/160-record coverage instead of shrinking the fixtures or mocking away storage.
- Repeat Defender tracing during equivalent work with comparable background activity, normalizing by completed jobs/tests as well as elapsed time. Faster tests can produce more work within a fixed 30-second trace, so raw scans per second alone can mislead. Report scan duration, total-system Defender CPU, and workload throughput separately. Do not claim a CPU fix from fewer Python file operations alone.
