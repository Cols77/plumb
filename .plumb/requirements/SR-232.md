---
id: SR-232
title: The log is append-only, one hash-chained file per entry
feature: FEAT-006
statement: 'Every log entry is written through one append function as its own JSON file under .plumb/log/<kind>/,
  created without replacing and never edited, carrying its digest and the previous entry''s digest found
  from a rebuildable head pointer; branches that both append never conflict and a forked chain is accepted.
  The only exception is the landing''s archive compaction (P15, SR-287), run and staged by the log module:
  it moves entry files, unchanged, into their kind''s append-only archive segment and removes the files;
  archived entries keep their digest and prev and stay part of the log for every reader except the hooks
  and session start. plumb validate reports an edited entry or archive line (caught by its own digest)
  and an unparsable file or line, but not a missing earlier entry, which may be another session''s or
  a local kind''s; the merge check refuses deleting a committed entry that no archive segment keeps (SR-322).
  An entry is visible to the next reader as soon as it is appended, within one worker pass too.'
examples:
- id: EX-1
  given: two worktrees that each append approvals, prompts and test runs
  when: one branch is merged into the other
  then: git reports no conflict under .plumb/log and plumb validate accepts the forked chain
- id: EX-2
  given: two writers in one worktree in the same second
  when: both append
  then: two distinct files exist and neither replaced the other
- id: EX-3
  given: a committed entry file edited by hand
  when: plumb validate runs
  then: it reports that file as modified
- id: EX-4
  given: the head pointer in .plumb/cache was deleted
  when: the next entry is appended
  then: its prev is the stream's latest entry, found by a scan
- id: EX-5
  given: an entry file deleted while a later entry names it as prev
  when: plumb validate runs
  then: it reports no log error, since the entry may be another writer's or a local kind's; the merge
    check refuses a merge that deletes a committed entry (SR-322)
- id: EX-6
  given: a file under .plumb/log that is not valid JSON
  when: plumb validate runs
  then: it reports the file as unparsable
- id: EX-7
  given: a batch of verdicts interrupted after some entries were written
  when: the next append runs
  then: it extends the chain from the last entry actually on disk, not from an older head pointer
- id: EX-8
  given: a worker pass running several jobs
  when: an earlier job appends its verdicts
  then: a later job in the same pass reads those entries, and the pass's final progress counts every job
