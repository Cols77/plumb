id: SR-206
title: An approval pins the exact content approved; any later edit goes...
feature: FEAT-001
statement: An approval, the owner's or the judge's, pins the hash of the record and of each acceptance
  test verifying it. While the pin matches the record is approved; never approved or reversed by the owner,
  it is proposed. Any later edit, a changed acceptance test included, makes it an unconfirmed edit that
  goes back through the judge cascade, held at the merge until approved again.
examples:
- id: EX-1
  given: an approved requirement
  when: its statement is edited
  then: it shows as an unconfirmed edit, not approved, and is handed back to the judge cascade
- id: EX-2
  given: a requirement never approved
  when: its status is read
  then: it is proposed
- id: EX-3
  given: a judge-approved requirement
  when: the owner says in conversation that it is wrong
  then: it returns to proposed, citing the owner's words
proof:
  plan: 'Recommended: in a scratch repository the owner sees a judge-approved requirement; the agent edits
    its statement and the status shows it as an unconfirmed edit until the judge approves it again; then
    the owner says in conversation that it is wrong and it returns to proposed. The owner decides whether
    this run is the proof.'
  kind: command
