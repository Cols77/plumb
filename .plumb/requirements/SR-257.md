---
id: SR-257
title: Record ids never collide across worktrees and clones
feature: FEAT-006
statement: 'Every new record id is reserved through one shared git ref with compare-and-swap, so worktrees
  of one repository never receive the same id. Ids that still collide across clones are renumbered at
  the merge: the branch merged into keeps its ids, the incoming record takes a newly reserved id with
  every reference its side introduced, history is never rewritten, an unchanged record keeps its approval,
  and the merge check holds any collision left.'
examples:
- id: EX-1
  given: two worktrees of one repository whose highest requirement is SR-069
  when: each creates a requirement at the same moment
  then: one gets SR-070 and the other SR-071, and refs/plumb/ids records 71 for SR
- id: EX-2
  given: a local branch that is not checked out holds SR-075 and refs/plumb/ids does not exist yet
  when: the first record is created
  then: the ref is seeded from every local branch and the new requirement is SR-076
- id: EX-3
  given: another process moved refs/plumb/ids between the read and the update
  when: the reservation's compare-and-swap fails
  then: plumb re-reads the ref and reserves the next free number, never reusing one
- id: EX-4
  given: a dry-run capture
  when: it previews the ids it would write
  then: refs/plumb/ids is unchanged
- id: EX-5
  given: a directory that is not a git repository
  when: a new requirement is created
  then: the record gets the highest local number plus one and the agent is told the id is not reserved
- id: EX-6
  given: a clone created SR-070 "export csv" while this repository created SR-070 "relay checks"
  when: the clone's branch is merged and merge-fix runs
  then: '"relay checks" stays SR-070, "export csv" gets the next reserved id, and every reference the
    clone added names the new id'
- id: EX-7
  given: 'the clone''s commits carry "SR: SR-070" trailers'
  when: merge-fix renumbers
  then: those commits are unchanged in git log, the claims check reads their trailers as the new id, and
    the merge message's trailer is rewritten
- id: EX-8
  given: '"export csv" was approved on the clone at its content'
  when: merge-fix renumbers it with no other change
  then: it stays confirmed under its new id, while an approval of different content is not carried
- id: EX-9
  given: a record on this repository's side that references SR-070
  when: merge-fix runs
  then: that reference still names SR-070
- id: EX-10
  given: merge-fix already ran
  when: it runs again
  then: it reports nothing to fix and writes nothing
- id: EX-11
  given: merge-fix renumbered "export csv" from SR-070 to SR-081 with no other change, and it had been
    approved
  when: the record is shown or the merge report lists approvals
  then: its confirmation is labelled "carried by renumber SR-070 -> SR-081", and any later edit of its
    words drops the carried approval
- id: EX-12
  given: a merge result in which two record files both declare SR-070
  when: the merge check runs
  then: it holds the merge with exit 1, names both files and says merge-fix fixes it; the agent runs merge-fix
    without asking the owner
- id: EX-13
  given: an in-progress merge with a requirement file both sides added
  when: the merge check runs on it
  then: it exits 1 with the collision named
- id: EX-14
  given: merge-fix has renumbered the collision
  when: the check runs again
  then: no collision is reported
proof:
  plan: 'Recommended for the owner to decide: one command script in a scratch repository creates a requirement
    in two worktrees at once and shows two different ids, then merges a clone that reused an id and shows
    merge-fix renumbering it with its references while git log is unchanged; the owner reads the printed
    before and after.'
