---
id: SR-230
title: A record is a Markdown file named by its id, hashed by its meaning
feature: FEAT-001
statement: plumb keeps every record (INT, SR, DEC, FEAT, NC) as a Markdown file with YAML frontmatter
  under .plumb/; its identity is its frontmatter id, never its filename; a malformed or duplicate id is
  reported. Its content hash covers the meaning (every frontmatter field except links, a requirement's
  proof and evidence, and the frozen marker of SR-380, plus the normalized body), so it ignores YAML style,
  key order, CRLF and trailing whitespace and changes when the meaning changes.
examples:
- id: EX-1
  given: a file .plumb/requirements/anything.md whose frontmatter id is SR-007
  when: plumb loads the records
  then: the record is SR-007, whatever the filename
- id: EX-2
  given: two record files that carry the same id SR-001
  when: plumb validate runs
  then: it reports a duplicate-id error naming both files
- id: EX-3
  given: a record whose frontmatter id is SR-1x
  when: the record is parsed
  then: it is rejected as a malformed id
- id: EX-4
  given: a record with a pinned hash
  when: the file is re-saved with CRLF line endings, reordered keys and trailing spaces
  then: its hash is unchanged
- id: EX-5
  given: a record with a pinned hash
  when: its statement is edited
  then: its hash changes and every link pinned to it goes stale
- id: EX-6
  given: a linked source file
  when: it is re-saved with CRLF line endings and no other change
  then: the file end's hash is unchanged
- id: EX-7
  given: a record whose only change is a new link in its links list
  when: its hash is computed
  then: the hash is unchanged, since links are not part of the meaning
proof:
  plan: 'Recommended for the owner to decide: the AI shows, in a scratch repository, a record renamed
    on disk still loading under its id, a CRLF re-save leaving its hash and links current, and a one-word
    change of its statement turning its links stale in the status.'
  kind: command
