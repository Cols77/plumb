---
id: SR-070
title: New record IDs are reserved through refs/plumb/ids
feature: FEAT-006
statement: Every new record ID (INT, SR, DEC, FEAT, NC and the intent-conflict IC) is reserved through
  one function that advances the shared ref refs/plumb/ids with git update-ref compare-and-swap, so two
  worktrees of one repository never receive the same ID; a lost race re-reads and retries, a dry run only
  peeks, imported IDs raise the high-water mark, and outside git plumb falls back to the highest local
  number plus one and says the ID is not reserved.
examples:
- id: EX-1
  given: two worktrees of one repository whose highest requirement is SR-069
  when: each creates a requirement at the same moment
  then: one gets SR-070 and the other SR-071, and refs/plumb/ids records 71 for SR
- id: EX-2
  given: a local branch that is not checked out holds SR-075 and refs/plumb/ids does not exist yet
  when: the first record is created
  then: the ref is seeded from every local branch and the new requirement is SR-076
- id: EX-3
  given: another process moved refs/plumb/ids between the read and the update
  when: the reservation's update-ref fails its compare-and-swap
  then: plumb re-reads the ref and reserves the next free number, never reusing one
- id: EX-4
  given: plumb capture --dry-run
  when: it previews the IDs it would write
  then: refs/plumb/ids is unchanged
- id: EX-5
  given: a directory that is not a git repository
  when: plumb new requirement runs
  then: the record gets the highest local number plus one and the output says the ID is not reserved
