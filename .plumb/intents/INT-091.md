title: plumb keeps itself fit at every landing, and parallel loops stay...
quote: Keep plumb fit by itself. Make the merge into main the place where cleanliness is enforced, so
  I never clean up by hand again
readback: 'Every merge into main runs one landing job: it tidies what the landed records replace and compacts
  the log (the tidy job already recorded), queues every record still waiting on a judge, and hands whatever
  the status still counts to a debug workflow the agent runs at its next turn, so the owner''s status
  card shows nothing stale, nothing waiting and no error. The merge itself refuses a landing that would
  add a validate error or a new stale link. The judge''s questions stop coming back malformed, and big
  judge jobs are split under the judge''s size limit. Parallel intent loops get three rough edges fixed
  (handing a loop to another session, the source path in a worktree, installs in a worktree), and no landing
  job touches another loop''s state.'
will:
- 'Run one landing job at each merge into main: the tidy and the log compaction already recorded, the
  judge backlog queued, and the leftovers written down as debug cases.'
- Refuse a merge into main that adds a validate error or leaves a new stale link, naming each to the agent;
  the owner is asked nothing.
- Queue the judge backlog at session start as well as at each landing, in jobs small enough for the judge.
- Accept a judge question that forgets which records it settles by taking the records of its job, and
  require that field in the judge's answer format.
- Have the agent run the debug cases at its next turn as a workflow on Sonnet, and say in the plumb line
  how many cases it resolved.
- Let a session take over an intent loop opened in another session, from the main checkout or a worktree.
- Make tests and plumb commands in a worktree use the worktree's own source without setting anything by
  hand, and let installs run from a worktree.
- Recognise /plumb intent and /plumb clarify when the owner pastes them.
- 'Keep every landing job off other loops'' state: their branches, gates, loop files, cards (except a
  merged branch''s) and records they changed.'
- 'Show it working on one real landing: a status card with nothing stale, nothing waiting and no error.'
wont:
- 'Touch the hand clean-up running in the other session: it lands first, as it is.'
- Start a background Claude run that commits to main by itself.
- Ask the owner about a leftover that is plumb's own problem; only an intent choice becomes a question.
- Approve anything on the owner's behalf other than through the judge.
- 'Compact the log or tidy on a branch: only main''s landing job does.'
assumptions:
- The real landing of the proof is this work's own landing, after the hand clean-up has landed.
- The merge check's refusal on a new stale link extends the existing one (a link the branch left stale)
  to validate errors; a link already stale at the merge base never holds the merge.
- Judge jobs are split at the judge's existing size limit, keeping an intent's records together when they
  fit.
- Handing a loop over is a plumb command the agent of the new session runs; the old session's loop is
  marked handed over and its gate released.
- A worktree's tests find their source through the test configuration, and plumb commands in a worktree
  prefer the worktree's source over the shared install.
- Only a paste that begins with the command counts; undo and auto-approve still have to be typed.
