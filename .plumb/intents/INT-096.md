title: The debug workflow improves plumb itself, through to a landed fix
quote: 'the debug workflow improves plumb itself: on a plumb failure it finds the cause, writes the failing
  test, fixes plumb, leaves nothing stale, passes the judge review and lands the fix on a branch; primarily
  in plumb''s own repo, on by configuration elsewhere; in the background on every failure and on demand
  with plumb debug'
readback: 'When plumb itself fails (a hook, job or command of plumb errors, a step refuses what it should
  handle, a judge job fails for the third time), plumb opens a debug case at once and, in the background
  while you keep working, works the case through to a fix of plumb: it gathers the evidence, reruns the
  step once, finds the cause in plumb''s code, writes the failing test, fixes plumb, runs the covering
  tests, repins every link the change moved, has the judge review that no requirement or intent changed
  meaning, and commits the fix on a branch of its own. Main waits for your word, as for any merge. This
  runs in full in plumb''s own repository; in another repository it runs only when its configuration turns
  self-debug on and names plumb''s source checkout, else the case ends with a defect report. You are asked
  only about an intent choice or what it cannot find. plumb debug runs the open cases on demand.'
will:
- open one debug case the moment a plumb hook, job or command errors, a step refuses what it should handle,
  or a judge job fails for the third time; the turn-end line stays quiet about it, and plumb debug shows
  the open and resolved cases
- run the self-debug workflow in the background, in a worktree of its own, without stopping your work
- stop a fix that would change what a requirement or intent means, and ask you one question through the
  question tool instead
- 'leave nothing stale after a fix: every link the change moved is repinned once its tests pass, or the
  case stays open'
- land each fix on a branch named for the case, with its failing test, the tests green and the judge review
  logged; never merge into main itself
- run as plumb's own command and skill, standing alone, with the cheapest model that fits each stage
- in another repository, do the same only when self-debug is turned on by configuration and plumb's source
  checkout is named; otherwise end the case with a defect report, say once what is missing, and, when
  issue reporting is turned on and the gh command is there, file that report once as an issue on plumb's
  GitHub repository
wont:
- change what a record means, approve anything, or merge into main
- ask you about plumb's own malfunction before trying to fix it, or ask what it can find in the log, the
  records or the code
- depend on any other plugin's or tool's skills
- 'keep trying without end: after three rounds the case is a defect report, not a fix'
- run in a repository that is not plumb's own unless its configuration says so
assumptions:
- 'A plumb failure is an error raised by a plumb hook, job or command, a plumb step that refuses what
  a requirement says it handles, or a judge job that fails at three turn ends in a row; a judge that cannot
  be reached is not one: that step holds and says so'
- 'The judge review of a fix is plumb''s usual one: the repin cascade for every link the change moved,
  and the record judge for any record the fix touches; a fix the judge says changes a requirement''s meaning
  is not committed'
- Each case runs in its own git worktree and branch, so the main checkout and your work are untouched
- 'The stages take the cheapest model that fits: evidence and the report on the smallest model, cause,
  test and fix on the middle one, the largest only when a round failed the tests or the judge'
- 'The configuration switch is a debug section in .plumb/config.yaml: self_fix on or off, and source,
  the path of plumb''s source checkout; on without a source names what is missing, once'
- 'The proof is tests only: acceptance tests with the models and git stubbed, no live session'
